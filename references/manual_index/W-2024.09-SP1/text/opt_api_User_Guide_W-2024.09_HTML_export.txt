Introduction

The optimizer library provides a common interface to access different underlying algorithms to perform
fittings in different tools such as Garand or Mystic. The main entry point for a user is the Fitter class, which
provides a series of built-in interfaces or backends that can be selected on creation and give access to
different sets of algorithms.

The Fitter class

The Fitter can be imported into any python environment as follows:

  from optimizer.fitter import Fitter

The backends available in the Fitter class are:  Description
   Interface

mkl_nls                                          Use Intel MKL nonlinear least squares solvers for
least_squares                                    bounded or unbounded problems.
minimize

doe                                              trust region, dogleg and Levenberg-Marquardt.
shgo

pymoo                                            residuals must be given in this case (RMS error by
                                                 default). Available minimisers include trust region, BFGS
                                                 (default), L-BFGS-B, COBYLA, etc.

                                                 Population based evolutionary algorithms for multi-

Parameters for the optimiser can be set using the Fitter.set_optimization_parameters method.

Target functions

There are a few things that need to be taken into account when defining a target function:

          By default, target functions are expected to take OptParam as input. However, it is possible to use
          target functions that take arrays instead if we pass the key wrap=False to the method do_fit .
          When using the Fitter class with most algorithms, the target function will receive multiple inputs to be
          processed (e.g. all the points needed for the Jacobian calculation), so they must be able to handle
          more than one input.
          Some methods will pass additional keyword arguments to the target (e.g. with doe and pymoo
          backends), so having optional keywod arguments in the definition will allow it to be used with every
          algorithm.

Examples                                                   that takes OptParam as input:

This example defines the function

# Define target function taking a list of OptParam
def target(p, **ignore):

      # Make sure it can handle 1D and 2D arrays for parallel
      # evaluation of Jacobian
      params = np.atleast_2d(p)
      return [[p[0].value**2 + p[1].value**2] for p in params]

# Select Optimization backend as doe
opt = Fitter("minimize")

# Define OptParams to be optimized
a = OptParam("a", 1., -2., 2., 1.)
b = OptParam("a", 1., -2., 2., 1.)

# Perform optimization
result = opt.do_fit([a, b], target)

Least squares backends

When using mkl_nls , least_squares , the following parameters can be used:

     ftol: Tolerance for termination by the change of the cost function (relative).
     xtol: Tolerance for termination by the change of the parameter (relative).
     gtol: Tolerance for termination by the change of the norm of the gradient of the cost function.
     max_nfev: Maximum number of function evaluations.
     verbose: Verbosity level, which can be from 0 (silent) to 2 (display information every iteration).

Other options specific to each interface are:

Interface                                       Option  Description

mkl_nls                                         method  Choice for bounded (bounded_trust_region) or
least_squares                                   trtol   unbounded (trust_region ) problem.
                                                delta
                                                method  Tolerance for termination by the size of the trust region.

                                                loss    Initial size of the trust region.

                                                        Least squares method. Can be one of `trf', `dogbox' or
                                                        `lm'.

                                                        Loss function used in the algorithm. Can be one of
                                                        `linear', `soft_l1', `huber', `cauchy' or `arctan'.

Examples

The following examples illustrate how to create the Fitter object, and change the solver and stopping criteria.

To create a Fitter object with the Intel MKL solvers backend, we would use the following:

  opt = Fitter("mkl_nls")

To change the Optimizer backend from Intel MKL Trust Region to scipy's implementations of least squares,
the command would be:

  opt.set_method("least_squares")

To change the solver used internally from TR (deafult solver for least_squares) to Levenberg-Marquardt:

  opt.set_optimization_parameters(method='lm')

To set all the tolerances to 1e-3:

  opt.set_optimization_parameters(ftol=1e-3, xtol=1e-3, gtol=1e-3)

With the previous definition of the target, not further changes are needed to use the doe backend:

  # Select Optimization backend as doe
  opt = Fitter("doe")

  # Define OptParams to be optimized
  a = OptParam("a", 1., -2., 2., 1.)
  b = OptParam("a", 1., -2., 2., 1.)

  # Set optimization parameters
  opt.set_optimisation_parameters(method="grid", options={'Ns':5})

  # Perform optimization
  result = opt.do_fit([a, b], target)

  # Print optimization result
  print(result)

To change the method whithin a backend, only a change in the setting of the optimization parameter is
needed. For example, to use Bayesian optimization after the previous example,:

  opt.set_optimisation_parameters(method="bayesian_optimiser", options={'Ns':10, "max_iter": 10})
  result = opt.do_fit([a, b], target)

SHGO

The shgo backend has two stages: first, a sampling of the space is done. Then, a triangulation of these
points is done and a local minimization is started at all locally convex points. The options for the local
minimization are the same the ones described for the backend minimize . Other options are:

                                                Dictionary with options for the solver. Posible keys are f_min (minimum

Example

The shgo backend needs the same options for the local minimization as minimize , but they need to be
passed in a different way:

  # Select Optimization backend as shgo
  opt = Fitter("shgo")

  # Define OptParams to be optimized
  a = OptParam("a", 1., -2., 2., 1.)
  b = OptParam("a", 1., -2., 2., 1.)

  minimizer_options = dict(method="SLSQP", options={"maxiter": 100})
  opt.set_optimization_parameters(n=20, sampling_method="sobol",

                                                        minimizer_kwargs=minimizer_options,
                                                        options={'disp':True})

  # Perform optimization
  result = opt.do_fit([a, b], target)

  # Print optimization result
  print(result)

Optimization Parameters

In order to define an optimization, we need to decide which parameters must be optimized and what values
they are allowed to take. In the optimizer library, this is done with a series of classes that provide a variety of
functionality:

OptParam

For the simpler problems, OptParam is the appropriate class to use. It is used to define continuous
parameters that do not require non-linear transforms during the optimization. The following options can be
specified when creating an OptParam:

name                                            Name of the model parameter, e.g. alpha.

TOptParam

In some situations, the dependence of the optimization target on the parameter is such that the problem can
be simplified if it is defined in terms of a transform of the parameter. For example, consider the following
problem shown linear and log scales:

The basin of the minimum is very narrow, so unless the initial value is close to the final solution, it will be
difficult to find it. However, after applying a logarithmic transform to the parameter, the basin of the minimum
widens for the same bounds, which makes it easier for the optimizer to find the minimum.

The parameters used to define a TOptParam are the same as those for OptParam except that instead of a
 scale parameter, there is a transform parameter and arguments for the transform can also be added:

Name       Description

transform  Transform to be applied to the parameter during the optimization
**kwargs   Additional keyword arguments to be passed to the parameter transform

There are two ways to define a transform for a TOptParam:

     Using the ParameterTransform classes
     Using one of the pre-defined transform strings

For example, to define a parameter with a decimal logarithmic transform, we could do:

  # Definition using a pre-defined string
  tp1 = TOptParam("param1", 0.1, 1e-2, 1e2, transform='decimal-log')

  # Definition using a Parameter transform
  from optimizer.parameters.transforms import DecimalLogarithmicTransform as Log10
  tp1 = TOptParam("param1", 0.1, 1e-2, 1e2, transform=Log10)

The transform argument

When TOptParam receives a transform, it will behave slightly diferent in the following cases:

Optimizer User Guide | W-2024.09 | HTML export

          If the transform is an instance of a ParameterTransform class, it will use it as-is.
          If the transform is a ParameterTransform class, it will be instantiated internall with arguments lower
          and upper set to the bounds of the parameter and any other keyword arguments passed to
           TOptParam .
          If the transform is a string, the corresponding ParameterTransform class will be instantiated internall
          with arguments lower and upper set to the bounds of the parameter and any other keyword
          arguments passed to TOptParam .

The ParameterTransform objects will be described in more detailed below, but there are a few things that need
to be considered when passing thems as arguments to a TOptParam object. For this purpose, we will
consider the case of NormalizeTransform , LogarithmicTransform and ScaleTransform , since they exemplify the
different cases that can arise in regards to arguments that need to be passed to a ParameterTransform :

           NormalizeTransform requires arguments lower and upper which will be mapped to the [-1, 1] range
          in the transformed space.
           LogarithmicTransform does not need any arguments.
           ShiftTransform needs a shift argument to define the factor used to scale the parameter values.

For example, to use the NormalizeTransform , the following three ways are equivalent:

  from optimizer.parameters.transforms import NormalizeTransform as Normalize
  p1 = TOptParam("p_instance", 3, 1, 10, transform=Normalize(1, 10))
  p2 = TOptParam("p_class", 3, 1, 10, transform=Normalize
  p3 = TOptParam("p_string", 3, 1, 10, transform="normalize")

Using multiple transforms

As with single transforms, there are also different ways to ask the TOptParam class to compose transforms:
          Using a camposed ParameterTransform instance
          Using a list or tuple with ParameterTransform instances, classes or strings

The first use case is straightforward:

  from optimizer.parameters.transforms import ShiftTransform as Shift
  from optimizer.parameters.transforms import LogarithmicTransform as Log
  t = Log() * Shift(3)
  p1 = TOptParam("p_instance", -1, -2, 97, transform=t)

The downside of this method is that for transforms that need the lower and upper arguments, it may be
cumbersome as they need to be transformed according to the previous transforms. For example,:

Optimizer User Guide | W-2024.09 | HTML export

     optimizer.parameters.transforms import DecimalLogarithmicTransform as Log10
     t = Normalize(-1, 2) * Log10() # Note that arguments for Normalize are in the log space p1 =

The second use case will instantiate the elements of the list/tuple using only arguments lower and upper ,
since other arguments could have clashing names (e.g. ScaleTransform and DualLog1pTransform both have a
 scale argument). This means that transforms that require other arguments such as Shift should be
instantiated explicitly. For example,:

     from optimizer.parameters.transforms import ShiftTransform as Shift from
     optimizer.parameters.transforms import LogarithmicTransform as Log
     p1 = TOptParam("p_class", -1, -2, 97, transform=[Log, Shift(3)]) p2 = TOptParam("p_string", -1, -2, 97,

The downside we saw for the previous method does not apply in this case, since the bounds are
automatically detected. The same example as above would be:

  from optimizer.parameters.transforms import NormalizeTransform as Normalize
  from optimizer.parameters.transforms import DecimalLogarithmicTransform as Log10
  p1 = TOptParam("p_class", 1, .1, 100, transform=[Normalize, Log10])
  p2 = TOptParam("p_string", 1, .1, 100, transform=["normalize", "decimal-log"])

  from optimizer.parameters.transforms import ShiftTransform as Shift

  p1 = TOptParam("p_mixed_class", -1, -2, 97, transform=[Normalize, t_shift])

LinkedOptParam

 LinkedOptParams are used to bind the value of a parameter to another existing parameter, so that they will
always take the same value. For example,:

  # Parameter with a default value of 2.0, bounded between 1.0 and 3.0 and with a scaling factor of 2
    alpha = OptParam("alpha", 2.0, 1.0, 3.0, 2.0)
    # New parameter linked to alpha. It will always have the same value as alpha.
    beta = LinkedOptParam("beta", alpha)
    assert alpha.value == beta.value

DOptParam

For discrete optimization parameters that take only a selected list of values, the syntax is slightly different,
since they are defined not by minimum and maximum values, but by the list of possible values that it can
take (choices):

  p = DOptParam(name, value, choices, sorted=False)

The final parameter, sorted, specifies whether to consider the listed values as ordered, that is, whether they
can be sorted in a meaningful way. This is usually related to the way in which the discrete parameter affects
the simulation.
To define a discrete parameter that can take the values ["a", "b", "c", "d"]we would use the following syntax:

  p = DOptParam("option", "c", choices=["a", "b", "c", "d"])

In this example, setting "option" to "a" or "b" represents an unrelated setting (for example, a change in
methodology), so using sorted=False would be appropriate. However, in some cases, the possible values
will define an order. In this case, you would define the discrete parameter as:

  p = DOptParam("option", "c", choices=["a", "b", "c", "d"], sorted=True)

This makes sense, for example, if the setting "option"="b" reflects an increased value of some parameter
with respect to "option"="a".

Error Calculation

The optimizer library provides several utitlities for error calculation which are divided in two groups. Residual
calculators do a point-by-point comparison of two sequences of data (usually one simulation output and one
reference or target data), and cost calculator aggregate a series of residulas into a single value.

Residuals

Residual calculators are used to obtain a (point-wise) distance between some data (d) and a target (t). The
following calculators are available in the optimizer library:

                                                "squared"

                                                "log_abs"

The following examples illustrate how to use the residual calculators:

  opt = Fitter("minimize")
  opt.set_optimization_parameters(options={'rhobeg':2.0})

  # Import factory for residual calculators
  from optimizer.targets.cost_functions import residual_generator

  # Define target function to accept OptParams
  def target(params, residual="signed"):

      res_calc = residual_generator(residual)
      reference = np.array([0.0, 1.0, 2.0, 3.0])
      myfunc = np.array([params[0].value, params[0].value + 1,

  # Define OptParams to be optimized

  b = OptParam("b", 1., -2., 2., 1.)

  # Perform optimization
  result = opt.do_fit([a, b], target)

  # Print optimization result
  print(result)

Costs

Cost, or loss, is a single-value aggregate of several residuals used to guide the optimization process. For
example, least squares methods typically use the sum of the squares of the residuals as the cost function:

The optimizer library provides the following costs that can be set by name using the method
set_cost_calculator:

cost calculator   name       function

RMSDCost (default) "rmsd"

LeastSquaresCost  "squared"
L1Cost            "l1"
SoftL1Cost        "soft_l1"

HuberCost         "huber"

CauchyCost        "cauchy"
ArcTanCost        "arctan"
SumOfResiduals    "sum"
MeanOfResiduals   "mean"

In the table above, are the weights for each residual and  .

 "rmsd" provides the root mean square deviation of the simulation outputs with respect to their target values.
The method "squared" is equivalent, that is, a minimizer of "rmsd" is a minimizer of "squared" , with the
advantage of smooth derivative at the minimum. On the other hand, its value can grow very fast due to the
squared dependence on the individual errors.

 "l1" , "soft_l1" and "huber" are similar for large values of the individual errors, which contribute to the
cost with a linear function of their absolute value.

Methods "arctan" and "cauchy" can limit large individual error contributions severely, with a cap to the
contribution for the former and with a logarithmic value for the latter.

 Note

The methods "sum" and "mean" simply add the individual residuals and are therefore not positive
definite. This means they may not always be appropriate as a measure of error, but they can be useful in
situations where a simulation output has to be minimized without reference to a target value, that is, you
are only interested in the simulation target achieving the lowest (possibly negative) value.

The following examples illustrate how to change the cost calculator for the Optimizer using the minimize
backend:

  opt = Fitter("minimize")
  opt.set_optimisation_parameters(jacobian_options={'eps': 1e-3})
  # Define target function taking a list of OptParam

          be given. In this case the option doe must be used.

Sensitivity and Screening Analysis

Sensitivity analysis can be used to understand how the variability of parameters affects the behavior of the
responses. There are two types of sensitivity analysis that can be performed: one-factor-at-a-time (OAT) and
the method of elementary effects (EE). OAT sensitivy analysis is mainly used for a local study around a
nominal point, whereas EE sensitivity analysis is more useful to consider global properties of the system.

A common use for Sensisitivity Analysis is the determination of the subset of parameters with the largest
impact on the problem. In this case we can talk of Screening Analysis. In this case the information is used to
determine how much the different parameters affect the simulation responses and rank them according to
their influence on each response, which can then be used to select a subset of parameters.

Local Sensitivity Analysis

Local Sensitivity Analysis and, in particular, one-factor-at-a-time sensitivity analysis aims at understanding
the response of the model as a function of small changes to a single parameter, with all other parameters
fixed. Therefore, it reveals only the local changes of the response surface of the model with respect to a
given parameter. Since the number of simulations only increases linearly with the number of parameters, it
can be provide a quick way to analyse the influence of different paramters and, if more than two points are
simulated in each direction, also their nonlinearity around the nominal point.

Global Sensitivity Analysis

In contrast to local sensitivity analysis, global sensitivity analysis aims to summarize information of the

complete domain, including interactions between parameters to some extent. The implemented

methodology, the method of Elementary Effects [Morris1991], [Campolongo2007] is based on aggregating

data from multiple one-factor-at-a-time experimental designs or trajectories. There are two parameters used

to define the analysis. nlevels determines how many levels each of the parameters can take. For example,

if there are four parameters in the analysis and nlevels=5 , then the total number of possible parameter

value combinations is                           (these are the possible values, not the actually simulated values). The other

parameter needed to define the analysis is ntrajectories , which determines how many trajectories are

executed. Each of this trajectories is local in the sense that:

1. Each trajectory has as many points as parameters in the study plus one. For example, for four
   parameters, each trajectory has 5 points.

2. In each trajectory, the coordinates can differ from the previous point in the trajectory in only one
   dimension and only by one step in the grid defined by nlevels .

3. In each trajectory, all dimensions must be changed exactly once.

The following figure shows an example of five trajectories in two dimensions using five levels for each
parameter.

Screening Analysis with Polynomial RSM

For some problems with many parameters you might be interested in selecting only a subset with the largest
impact. You can use screening analysis to determine how much the different parameters affect the
simulation responses. Parameters are then ranked according to their influence on each response, and this
information can be used to select a subset of parameters. Due to the possibly large number of parameters,
this task uses a polynomial response surface model (RSM) built from a given DOE such as a Plackett-
Burman design. These RSMs are used to obtain the effect of each parameter on the simulation responses.
This is done using the normalized coefficients of the RSMs build from the normalized parameters to

                                                                                                                                                                                                                                                     41 / 48
Optimizer User Guide | W-2024.09 | HTML export

rank parameters according to their effect on the responses. Using a polynomial model across the design
space allows taking into account interactions between parameters, but it requires the data to be well
approximated by the model.

   Note
  If two parameters are influential through their interaction they will both be selected.

Response Surface Models

Response surface model (RSM) objects provide a convenient interface to create RSM from available data
(e.g. from simulation done at some given DoE points). There are different types of supported RSMs such as
polynomials and Gaussian processes that can be appropriate depending on the nature of the data.
Examples
The following example illustrates the creation of a polynomial response surface object to represent the data
stored in the arrays x and y:

  # Parameters that describe the space of the problem
  p1 = OptParam("p1", 0.5, 0, 1)
  p2 = OptParam("p2", 0.5, 0, 1)
  # Data from some simulation
  x = np.random.uniform(0, 1, size=(10, 2))
  y = np.sin(x[:, 0])*np.sin(x[:, 1])
  # Define a quadratic polynomial RSM for the space defined by p1 and p2
  poly = PolynomialRSM([p1, p2], order=2)
  # Create the model from the data
  poly.create(x, y)
  # Print summary of the fit quality
  print(poly.fit_summary)
  # Test at some additional points
  x = np.random.uniform(0, 1, size=(10, 2))
  y = np.sin(x[:, 0])*np.sin(x[:, 1])
  r2 = poly.score(x, y)
  print(f"r2 = {r2}")

If instead of a polynomial a Gaussian process is more appropriate:

  # gaussian process RSM for the space defined by p1 and p2
  gp = GaussianProcessRSM([p1, p2])
  # Create the model from the data
  gp.create(x, y)
  # Test at some additional points
  x = np.random.uniform(0, 1, size=(10, 2))
  y = np.sin(x[:, 0])*np.sin(x[:, 1])
  r2 = gp.score(x, y)
  print(f"r2 = {r2}")

Gaussian Process Kernels

Gaussian process RSMs used to fit an n-dimensional Gaussian process to the provided targets are
characterized by a kernel that determines the smoothness of the approximating surface. By default, the
kernel used is Matern32, which is one time differentiable and therefore does not enforce too much
smoothness. For a two times differentiable version, Matern52 could be used and for an infinitely
differentiable kernel, SquaredExponential would be appropriate.

The available kernels are:

kernel              parameters description

Matern              l_scale                     characteristic length scale
                    nu                          order of the kernel
Matern32            l_scale                     characteristic length scale
Matern52            l_scale                     characteristic length scale
NeuralNetwork       sigma                       variance parameter for input
                    sigma_0                     variance parameter for constant term
RationalQuadratic   alpha                       rational exponent
                    l_scale                     characteristic length scale
SquaredExponential  l_scale                     characteristic length scale

Examples
The following examples illustrate how to create a GP RSM with different kernels in one dimension:

  # 1D example
  x = np.random.uniform(size=(10, 1))
  y = ((x-0.5)**2).ravel()
  p1 = OptParam("p1", 0.5, 0, 1)
  # Fit Gaussian process with Matern52 kernel
  kernel = Matern52(l_scale=1)
  model = GaussianProcessRSM([p1], kernel=kernel)
  model.create(x, y)
  x_pred = np.linspace(1e-2, 1, 100).reshape((-1, 1))
  pred = model(x_pred)
  # Fit Gaussian process with SquaredExponential kernel
  kernel = SquaredExponential(l_scale=1)
  model = GaussianProcessRSM([p1], kernel=kernel)
  model.create(x, y)
  pred = model(x_pred)
  # Fit Gaussian process with Matern 7/2 kernel
  kernel = Matern(nu=3.5, l_scale=1)
  model = GaussianProcessRSM([p1], kernel=kernel)
  model.create(x, y)
  pred = model(x_pred)
  # Fit Gaussian process with Matern52 kernel
  kernel = NeuralNetwork(sigma_0=1, sigma=1)
  model = GaussianProcessRSM([p1], kernel=kernel)
  model.create(x, y)
  pred = model(x_pred)

  # Evaluate goodness of fit
  gof = model.score(xtest, ytest)
